# @tiaforge-ui/sinter-markdown

Markdown for [sinter](https://github.com/tiaforge/sinter): a parser, `md.parse`, that returns a tree,
and components, `<md-doc>` and `<md-inline>`, that render it. Markdown from a file in the repo is plain
HTML at build time; markdown from an API is parsed in the browser. How a kind of node looks is changed
with slots.

```html
<sn-resource name="post" src="file:./post.md"></sn-resource>
<main data-sn-let="{ doc: md.parse(post.body) }">
  <md-doc data-sn-with="{ doc }"></md-doc>
</main>
```

**Using it:** [docs/markdown.md](docs/markdown.md), and the [recipe](docs/recipes/article-with-comments.html)
with an article and its comments on one page.

This package is also the example to copy when you write a [component
library](https://github.com/tiaforge/sinter/blob/main/docs/libraries.md) of your own. The rest of this
file is about that: what each part is, why it is where it is, and how the library is checked and tested.

## Using it in an app

```sh
npm install @tiaforge-ui/sinter-markdown
```

```js
// vite.config.js: the package is a component library
sinter({ libraries: ['@tiaforge-ui/sinter-markdown'] })
```

```ts
// src/sinter.helpers.ts: its helpers, under a namespace the app chooses
export * as md from '@tiaforge-ui/sinter-markdown';
```

```ts
// src/sinter.types.ts: its types, where the app's own declarations name them
export type { Root } from '@tiaforge-ui/sinter-markdown';
```

That is all an app does with a library: name it in the config, re-export its helpers and types. The
public components (`<md-doc>`, `<md-inline>`) are then tags on every page. To make the parser load on
demand, the app also lists the package in `sinter({ lazy })` ([docs](docs/markdown.md#three-places-one-function)).

## The package


### `package.json`

```json
{
  "name": "@tiaforge-ui/sinter-markdown",
  "type": "module",
  "sinter": "./sinter",
  "exports": {
    ".": "./sinter/index.ts",
    "./parser": "./sinter/parser.js"
  },
  "peerDependencies": { "@tiaforge-ui/sinter": ">=0.18.0 <1" }
}
```

- **`"sinter": "./sinter"`** names the folder that sinter reads as the library's source. A library
  ships source, not built output: the app's sinter compiles its components as it compiles the app's
  own, so they get build-time constants, the early script, type checks and scoped styles.
- **`exports`.** `.` is the entry, which re-exports the helpers: the app's
  `export * as md from '@tiaforge-ui/sinter-markdown'` is followed through it to each helper's own
  module. `./parser` lets `parse.ts` import the parser by the package's name (below).
- **`peerDependencies`** lists the sinter versions the library supports. The app's sinter warns when
  its version is outside the range (`SN537`). sinter is a peer, never a dependency: the app has one
  sinter, and the library's markup is compiled by it.
- **`devDependencies`** hold what builds and tests the library: the parser's sources (bundled into
  `parser.js`, so an app installs none of them), the bundler, and a sinter to test against (`file:../..`
  in this repository, the framework's own build).

### The components

- **Public and internal.** `components/` is what apps use; `components/internal/` is the library's own
  (`SN339` if an app uses one). Every name starts with the library's prefix, `md-`, which the library
  owns: no app component and no other library may use it.
- **The contract is in the public files.** `md-doc.html` and `md-inline.html` declare the slots an app
  fills (`heading: Slot<{ node: Heading }>`, …); the internal components place them
  (`<slot name="heading" data-sn-with="{ node }">`) without declaring them, as [tree
  slots](https://github.com/tiaforge/sinter/blob/main/docs/components.md#tree-slots). Adding a slot
  later is additive; renaming or removing one breaks apps.
- **Roots.** A component's root renders at most one element. A heading is an if chain over its depth,
  a list over `ordered`, and a node an app can change has its slot as its root, with the default
  inside. A root that is not a plain element costs nothing when a constant decides it.
- **Dispatch in one place.** `md-block` chooses a block's component by its type, and `md-phrasing`
  an inline node's: each is a component whose root is `<sn-component use="{ paragraph: 'md-paragraph',
  … }[node.type]">`, one choice per node whatever the number of candidates. Every loop over children
  renders `<md-block>` or `<md-phrasing>` for each, so each map is written once. A component whose root
  is the choice adds no element and no anchor of its own. In a library with slots the map (or
  convention) form is required, so sinter knows every candidate (`SN312`).
- **Text runs** are `<template data-sn-text>`, a text node with no element around it. A root cannot be
  text, so text runs are not a component: each loop over phrasing content writes
  `<template data-sn-if="n.type === 'text'">` for them and passes every other node to `<md-phrasing>`.
  `test/components.test.ts` checks that every such loop has that form.
- **Phrasing roots for phrasing places.** `md-inline` is used inside headings, labels and paragraphs,
  so its root is a `<span>` and everything in it is phrasing content. A `<div>` there is invalid, and
  in a `<p>` the HTML parser would close the paragraph, so a page built at build time would be
  reparsed into a different tree. Since it renders no headings, code blocks, quotes or tables, it
  declares only the slots it places (`link`, `image`, `inlineCode`): every declared slot must be placed
  (`SN331`).

### The helpers

- **Two modules, one namespace.** `md.parse` is in `parse.ts`, which imports the parser; `md.headings`
  and `md.text` are in `tree.ts`, which does not. sinter decides per module whether a helper waits for
  a lazy package, so with the parser lazy, `md.headings` stays an ordinary helper that renders early
  and folds at build time. `sinter.helpers.ts` re-exports both, and the entry re-exports it.
- **Pure.** A helper over constants (a `file:` resource) runs at build time, if everything it reaches
  uses only the language's own globals and `URL`, `URLSearchParams`, `structuredClone`, `TextEncoder`
  and `TextDecoder`. `parse.ts` and `tree.ts` are written that way, and so is the parser; sinter's check
  reads a top-level `const x = memo(…)` as a unit of its own, so the memo's cache does not stop
  md.parse from folding.
- **md.parse keeps its trees.** In the browser a let or a prop is its expression, evaluated at every
  read, and md-doc's components read their `doc` at every node: an article's let is read hundreds of
  times per render. So `parse.ts` wraps the parse in sinter's `memo()`
  (`@tiaforge-ui/sinter/memo`), and the contract is:
  - the same source and the same options give the same tree object, parsed once. The options are
    normalized first (defaults filled in, `base` with its trailing `/`), so `{}` and
    `{ html: 'text' }` share a tree;
  - the tree is deep-frozen and shared by every caller, in production too: change a copy
    (`structuredClone(doc)`);
  - the cache holds about 8 MiB of trees, the least recently used going first; a source whose tree was
    dropped is parsed again, into a new tree;
  - an invalid option throws at each call, and nothing is kept.

  Measured in Node on the spike's 47.5 kB article: a parse takes about 67 ms, a read of a kept tree
  about 0.01 ms. On its recipe page, the browser parses each distinct source once
  (`test/parses.test.ts`); without the memo it parsed 16 times for 6 sources. Each bundle keeps its own
  trees (the page module, the early file) and the build its own, at build time.
- **md.headings and md.text walk the tree at each read**, with no cache: they take a tree, an object,
  which `memo()` would call through anyway. On the 47.5 kB article they take about 0.09 and 0.2 ms, on
  50 comments about 0.01 and 0.05 ms together; a page reads them a few times per render, not per node.
- **Nothing per node is kept in the components.** None has state, a script or a handler, so two
  comments with the same body share one frozen tree and render it twice, each in its own rows.
- **The library's components cannot call its helpers.** In markup, helpers are called through the
  namespace the app chose (`md.` here, but the app could write `export * as markdown from …`). What a
  component needs is computed into the data instead: `md.parse` writes each heading's `slug`.

### The parser: one prebundled module

`parser.js` is markdown-it (CommonMark, GFM tables and `~~strikethrough~~`) with GFM's autolinks
(`scripts/autolink.js`), configured for `md.parse` and bundled into one file by `scripts/build-parser.mjs`:
21.8 kB minified and gzipped (19.5 kB brotli). It returns markdown-it's tokens, and `parse.ts` builds the
tree from them in one pass, task lists and the options included: there is no intermediate tree (an mdast
before the library's own, and a walk over it).

- **markdown-it, not micromark**, for speed: on a 47.5 kB article it parses in 23 ms on a cold start
  where micromark took 160 ms, which was most of an API article's time to first render. GFM is what
  markdown-it gives, and GFM's autolinks: `~one tilde~` is not strikethrough. Everything CommonMark
  specifies gives the same tree as micromark did, except a code span's line endings, which are spaces,
  as CommonMark renders them.
- **What `md.parse` never runs is left out**, so the bundle holds markdown-it's parsers and rules and
  no more: its renderer, the typographer's rules (`typographer` is off) and its linkify are
  `scripts/unused.js`; mdurl (`scripts/mdurl.js`) and punycode (`scripts/punycode.js`) are left out
  because the tree keeps a link's destination as written, so the parser normalizes no URL; uc.micro's
  tables are two regexes (`scripts/uc-micro.js`: emphasis needs Unicode punctuation and symbols, `\p{P}`
  and `\p{S}`). The parser was 34.5 kB with them. `test/parse.test.ts` checks which of markdown-it's
  modules are in it.
- **Autolinks are GFM's** (`scripts/autolink.js`, a core rule run after markdown-it's): `www.`,
  `http(s)://` and `ftp://` URLs, emails, and `mailto:` and `xmpp:` emails, as github.com finds them.
  A bare domain is not a link (`example.com`, `config.md`), a bare email is
  (`foo@bar.baz`, to `mailto:foo@bar.baz`), and the end of a link is trimmed as GFM specifies: trailing punctuation, a
  `)` with no `(`, an entity-like `&hl;`. It passes the GFM spec's and cmark-gfm's autolink examples,
  which markdown-it's linkify (linkify-it) got about half of, and is about 1 kB where linkify-it and its
  Unicode tables were about 5.7 kB. Only those schemes come out. It is linear in the text: every match
  moves the scan forward and a link's end is trimmed by an index; `test/parse.test.ts` parses long runs
  that a backtracking scan revisits (`a.a.a.…`, `www.a.b)))…`, `&a;&a;…`) within a second each (each
  takes under 0.1 s).
- **Entities decode from a table** (`character-entities`, through `scripts/entities.js`), never through
  the DOM, so the parser works under Trusted Types (`require-trusted-types-for 'script'`). It is the
  table micromark used, packed by `scripts/build-parser.mjs`: sorted by code point, each entry its
  distance from the one before, about 7.5 kB gzip where the table as an object is 11.5 and
  markdown-it's own (`entities`, a packed trie) 21. It is unpacked once, when the parser loads.
- sinter's build-time check follows one module that uses no browser global, so `md.parse` folds over
  a `file:` resource.

**Committed, not built on install.** The built file is in the repository and in the published package,
and a test fails when it is not what the script writes from the locked dependencies
(`npm run build:parser -- --check`). Building on install would need the bundler and the parser's
sources in every app's install, and a step that can fail there; a committed file is reviewed like any
change, and is the same file in every app. After updating a parser dependency, run
`npm run build:parser` and commit the result.

`parse.ts` imports it as `@tiaforge-ui/sinter-markdown/parser`, through the package's own `exports`,
not as `./parser.js`: an app makes a package lazy by name (`sinter({ lazy })`), and sinter matches lazy
packages by import specifier.

### Fixture pages

A library has no pages, and sinter checks a component through the pages that use it. `fixtures/*.html`
are pages that use the public components with the cases the library supports: an article from a
file, every slot filled, comments from an API. `npx sinter check` in this folder takes them as its
pages (there is no Vite config with pages of its own), configures the package as a library of
`sinter({ libraries })`, compiles and type-checks them, and checks the library's rules: every declared
slot is placed somewhere (`SN331`), `<sn-component use>` takes a map (`SN312`), internal components are
used only inside the library (`SN339`). Each app's build checks the same rules again.

`vite.config.ts` points the check at `fixtures/sinter.helpers.ts` and `fixtures/sinter.types.ts`, which
are what an app would write: the package re-exported by its own name (`export * as md from
'@tiaforge-ui/sinter-markdown'`, which works because the package has `exports`).

## Checking and testing

```sh
npm install             # in this folder
npx sinter check        # the fixture pages: compiled, type-checked, the library's rules
npm run typecheck       # parse.ts, tree.ts and the tests
npm test                # vitest
```

In this repository the package is tested against the framework's own build: run `npm ci && npm run
build` at the root first. CI runs the package's tests in a job of its own, after the framework's build.

| Test | What it covers |
| --- | --- |
| `test/parse.test.ts` | `md.parse` and its options, `md.headings`, `md.text`; that `tree.ts` imports no parser; that `parser.js` is up to date and decodes entities with its table |
| `test/check.test.ts` | `sinter check` over the fixture pages: no error, no warning |
| `test/static.test.ts` | a page with `<sn-resource src="file:./post.md">` built with `sinter({ static })`: no JavaScript, every node type as plain HTML, `html: 'allow'`, the table of contents, a local image optimized |
| `test/parses.test.ts` | the recipe in Chromium with the parser counting what it tokenizes: one parse per distinct source, none after a change elsewhere on the page or for a new comment with a body already parsed |
| `test/components.test.ts` | the dispatch maps against the `Block` and `Inline` unions and the component files, and the form of every loop over phrasing content |
| `test/api.test.ts` | the recipe built as an app, served with an API, in Chromium under `script-src 'self'; style-src 'self'; require-trusted-types-for 'script'`, failing on any violation or console error: entities, the user-content policy, the link fill, unsafe URLs, images; with the parser loaded with the page and with it lazy |

`test/app.ts` makes a throwaway app with the package linked into its `node_modules`, as a workspace or
`npm link` does: the tests use the package the way an app does.

## Notes for library authors

What writing this library taught, beyond [the library docs](https://github.com/tiaforge/sinter/blob/main/docs/libraries.md):

- **Whitespace between tags is text.** Inside a component, a newline and indentation between two tags
  is a text node in the page, once per row of a loop: in phrasing content it shows as a space. The
  components here write the markup inside each root without whitespace between tags.
- **Text runs first.** For the children of a paragraph, `<template data-sn-if="n.type === 'text'">` the
  text, `<template data-sn-else>` the choice, costs one anchor per text run. The choice first with a
  `data-sn-else` for text costs two: the choice's anchor, empty for text, and the else's own.
  `sinter check` narrows each branch by its condition, so `n.value` and `n.type` are typed in both.
- **An id from data starts with a literal.** `data-sn-attr="{ id: node.slug }"` warns (`SN503`): an id
  written from data can shadow a global another script reads. The anchors are `'md-' + node.slug`, and
  `md.headings` returns the same ids, so a table of contents and the anchors agree.
- **A slot inside a `<table>` cannot be written in a fill.** The HTML parser moves a `<slot>` written
  inside a `<table>` out of it, so a fill cannot place a table's rows. The `table` slot's default is
  therefore a `<div class="md-table">` around the table: a fill places the whole table, or renders its
  own.
- **An image from user content is a plain `<img>`.** `md-image` binds `srcset: null`, which tells sinter
  not to send the image through the app's resizing service; an app that wants it resized fills the
  `image` slot.
- **A candidate that cannot match is a warning.** Under the else of `data-sn-if="b.type === 'paragraph'"`,
  a map that still lists `paragraph:` names a component that never renders there (`SN538`).
- **Count what renders.** A separator between items (md-inline's space between paragraphs) goes
  before every item but the first of the list that renders: md-inline loops over
  `doc.children.filter((x) => x.type === 'paragraph' || x.type === 'heading')`, so a list it leaves out
  first adds no leading space. TypeScript narrows the filtered items to `Paragraph | Heading`.

### Adding a node type

1. Its interface in `sinter/sinter.types.ts`, with its `type` literal, and the interface in the `Block`
   or `Inline` union.
2. Its conversion from markdown-it's tokens in `sinter/parse.ts` (`blocks()` or `inlines()`), and its text in `md.text`
   (`sinter/tree.ts`) if it has no `children` or `value`.
3. Its component in `sinter/components/internal/`, named with the `md-` prefix.
4. One entry in the map of `md-block.html` or `md-phrasing.html`. `test/components.test.ts` fails until
   the map and the union agree and the component exists.
5. If apps should be able to change it, a slot: declared in `md-doc.html` (and `md-inline.html` for
   phrasing content), placed as the new component's root.
